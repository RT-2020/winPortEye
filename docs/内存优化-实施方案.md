# 内存优化实施方案（vibe-guard 守卫）

> 目标：把 PortEye 单次端口扫描的内存分配从 **2.3MB / 1895 次** 降下来，手段是用原生 Win32 API 替换 gopsutil 依赖。
>
> 本方案按 `vibe-guard-pure` 的闭环编写：resolve roots → baseline → pin intent/plan → apply gates → implement → inspect → report。

---

## 0. 执行摘要

| 维度 | 结论 |
|---|---|
| 风险等级 | **Medium**（跨多文件、涉及依赖移除；步骤 2.5 的 Cmdline 改造涉及跨进程内存读取，Security 轴偏高，但公共契约不变） |
| 决策权限 | 可自主执行（详见 §3 决策权限分析） |
| 公共契约影响 | **无**（`core.Connection` / `ProcessInfo` / `KillResult` 类型与字段不变，`ListConnections` 等签名不变，字段语义保持） |
| 依赖方向影响 | **无新增方向**（外部依赖 gopsutil → 缩减为对 kernel32/iphlpapi 的 syscall，方向仍为 core → 系统） |
| 兼容性 | Vista+ 原生系统组件，**不缩小**当前「Win7+」支持范围 |
| 回滚 | 普通 `git revert`，无数据/运行时迁移 |
| 需用户协助 | 仅步骤 3（端口枚举）需真实环境对比验证一次 |

> **关于"公共契约不变"的精确含义**：类型定义和函数签名不变，但 `ProcessInfo.CommandLine` 的**实现路径**会变（步骤 2.5 从 gopsutil 改为自实现 PEB 遍历）。可观察行为保持一致——对权限不足/系统进程仍返回空串，与现状相同。

### 1.4 性能 Baseline（实测证据）
单次 `ListConnections(KindAll)`：
- 耗时：3.2ms
- 内存：**2.3MB / op，1895 allocs/op**
- 分配热点（200 次 × alloc_space profile，累计 452MB）：
  - `process.ExeWithContext`：**351MB（77.8%）** ← 最大头

| 轴 | 评级 | 依据 |
|---|---|---|
| Scope | Medium | 跨 4 文件（scanner/process/killer）+ 新增 2 文件（winapi、cmdline） |
| Contract | **Low** | 公共类型/函数签名与字段语义零变更（见 §4.1 契约冻结） |
| Dependency | **Low** | 移除外部依赖 gopsutil，新增对系统 DLL 的 syscall；**无新跨层方向**，core 仍单向依赖系统 |
| Data | Low | 无持久化影响 |

## 3. 边界 Gate（复用/抽取判定）

本次新增一个 `internal/core/winapi.go` 封装 syscall。按 reuse-and-boundaries 的 gate 判定：

### Gate A — 自然归属
- **归属**：`internal/core` 包（与 scanner/process/killer 同包，天然 owner）
- **不放 utils/common**：✅ 不创建通用层，winapi 是 core 的私有实现细节

### Gate B — 一致性审问
1. **Owner**：`internal/core` 包，与进程/端口逻辑同生命周期
2. **Responsibility**：单一职责——封装 PortEye 用到的 5 个 Win32 syscall（OpenProcess / QueryFullProcessImageNameW / TerminateProcess / GetExtendedTcpTable / GetExtendedUdpTable）
3. **Counterfactual**：即便只 scanner 用，作为同包私有文件仍合理（把 unsafe/syscall 集中，避免散落各处）
4. **Contract**：包内私有，不对外暴露
5. **Change direction**：Win32 API 极稳定（Vista+ 未变），改动频率低

**结论**：通过。这是同包内的实现集中，不是跨层抽取。

## 4. 契约冻结（不变量）

### 4.1 公共契约（必须保持不变）
这些是 `core` 包对外暴露的契约，`ui`/`mcpserver` 依赖它们，**改动后签名与语义必须一致**：

```go
// types.go —— 类型不变
type Protocol string           // "tcp"/"udp"
type Connection struct { ... } // 9 个字段不变
type ProcessInfo struct { ... }// 4 个字段不变
type KillResult struct { ... } // 3 个字段不变

// scanner.go —— 签名不变
func ListConnections(kind FilterKind) ([]Connection, error)
func FindPort(port uint16, kind FilterKind) ([]Connection, error)

// process.go —— 签名不变
func GetProcessInfo(pid int32) (ProcessInfo, error)

// killer.go —— 签名不变
func KillProcess(pid int32) KillResult
func KillByPort(port uint16, kind FilterKind) ([]KillResult, error)
```

### 4.2 行为不变量（必须验证）
| 不变量 | 验证方式 |
|---|---|
| 端口枚举结果集合一致（TCP/UDP × v4/v6） | 步骤 3 真实对比 |
| 进程名 = `filepath.Base(完整路径)` | 单测 |
| 权限不足时 Name/Path 返回空字符串（非报错） | 单测 + 对比 |
| `Connection.State` 字符串格式逐值复刻 gopsutil | 单测（含 12 项 TCP 状态 + UDP="NONE"） |
| UDP 行的 State 必须为 `"NONE"`（原生 UDP 表无 state 字段） | 单测 |
| `Connection.Protocol` 由"来自哪张表"隐式确定（非 Type 字段） | 单测 |
| `ProcessInfo.CommandLine`：权限不足/系统进程返回空串（与现状一致） | 单测 + 对比 |
| `ProcessInfo.CreateTime` 单位为毫秒（与现状一致） | 单测 |
| `PidExists` 返回 false 时 KillProcess 返回"进程不存在" | 单测 |
| 两级杀进程语义：直接杀失败 → runas 提权 | 单测覆盖路径 |

### 4.3 依赖方向不变量
- `ui → core`、`mcpserver → core`：不变
- `core → 系统`：从「core → gopsutil → 系统」简化为「core → 系统（直接 syscall）」，**方向不变，只是层数减少**

## 5. 兼容性背书（已调研，详见上轮对话）

| API | DLL | 官方最低要求 | 当前支持范围 | 结论 |
|---|---|---|---|---|
| `GetExtendedTcpTable/UDP` | iphlpapi.dll | Vista / XP SP2 | Win7+ | ✅ 完全覆盖 |
| `QueryFullProcessImageNameW` | kernel32.dll | Vista | Win7+ | ✅ 完全覆盖 |
| `TerminateProcess` | kernel32.dll | Windows 2000 | Win7+ | ✅ 完全覆盖 |
| `OpenProcess` | kernel32.dll | Windows XP | Win7+ | ✅ 完全覆盖 |

**关键事实**：gopsutil 底层就是调这几个 API（已核实 `net_windows.go:19-22`、`process_windows.go:342-367`）。本次改动是「去掉 gopsutil 胶水，直接调同一组 API」，**功能等价，仅减少中间层开销**。

**降级点**：iphlpapi/kernel32 是 Windows 核心组件，不可卸载、不会被组策略禁用。唯一需要运行时检测的是 `QueryFullProcessImageNameW` 是否存在（用 `LazyDLL.Find()`），但 Vista+ 必然存在，检测只是防御性编程。

## 6. 分步实施计划

> 每步独立可验证、独立可提交。严格按顺序，因为后步依赖前步。

### 步骤 1：合并 Name/Path 查询（最低风险，立竿见影）

**目标**：消除「同一 PID 查两遍完整路径」的重复。

**改动**：
- `process.go`：合并 `getProcessName` + `getProcessPath` → 单个 `getProcessNamePath(pid, cache) (name, path string)`
- `scanner.go`：`ListConnections` 改用合并后的函数，缓存 key 仍为 PID
- 仍走 gopsutil（本步不换 API），只是不再查两遍

**契约**：不变（`getProcessName/Path` 是包内私有，可改）

**验证**：
- `go test ./internal/core/` 通过
- benchmark：预期 allocs 下降 ~40%（进程查询是 77.8% 大头，去掉一半重复）

**风险**：极低。纯逻辑去重。

---

### 步骤 2：进程 Name/Path 改原生 API（核心收益）

**目标**：用 `QueryFullProcessImageNameW` 替换 gopsutil 的 `ExeWithContext`/`NameWithContext`，砍掉 77.8% 的分配大头。

**改动**：
- 新建 `internal/core/winapi.go`：封装 `OpenProcess` + `QueryFullProcessImageNameW`
  - 进程级复用 `[]uint16` 缓冲区（避免每次 `make`）
  - `LazyDLL.Find()` 防御性检测 API 存在性
- `process.go`：
  - `getProcessNamePath` 改用 winapi（不再走 gopsutil）
  - `GetProcessInfo` 的 Name/Exe 改用 winapi
  - **本步只改 Name/Exe**；`Cmdline`/`CreateTime` 仍走 gopsutil，留到步骤 2.5 处理

**契约**：`ProcessInfo` 结构不变，`GetProcessInfo` 签名不变。

**验证**：
- 新增 `process_test.go`：对比 winapi 与 gopsutil 对同一 PID 的 Name/Path 结果一致
- `go test ./internal/core/` 通过
- benchmark：预期进程查询分配从 351MB → 接近 0（只剩 Go 字符串本身）

**风险**：低。单 API 调用，有 gopsutil 参照实现可对照。

---

### 步骤 2.5：替换 Cmdline / CreateTime（解除 gopsutil 的最后依赖）

> 本步是审查 Issue 1 的修复项。步骤 2 只改了 Name/Exe，但 `GetProcessInfo` 的 `Cmdline`/`CreateTime` 仍走 gopsutil——若不处理，步骤 6「移除 gopsutil」的前置条件（代码无 gopsutil 引用）永远无法满足。本步解除这最后依赖。

**目标**：用原生 API 替换 `Cmdline`/`CreateTime`，使 `process.go` 完全不再 import gopsutil。

**改动**：

- **`CreateTime`（简单）** → `GetProcessTimes`
  - `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetProcessTimes` 取 `CreationTime`（FILETIME）→ 转毫秒（自 epoch）
  - gopsutil 的 `createTimeWithContext` 就是这个实现，可直接参照
  - 权限不足返回 0（与现状一致）

- **`Cmdline`（复杂）** → 自实现 PEB 遍历
  - 需要 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ)`——比 Name/Exe 多要 `VM_READ`，权限门槛更高
  - 流程：`NtQueryInformationProcess` 取 PEB 地址 → 按 32/64 位分别解析 `RTL_USER_PROCESS_PARAMETERS` → `ReadProcessMemory` 读 `CommandLine` 字符串
  - **对系统进程/受保护进程必然失败**，降级返回空串（与现状一致，行为不变量已在 §4.2 锁定）
  - 实现参照 gopsutil 的 `getProcessCommandLine`（v4.26.7 `process_windows.go`）
  - 新建 `internal/core/cmdline.go` 集中放这块逻辑（避免污染 winapi.go）

**契约**：`ProcessInfo` 的 4 个字段定义不变，`GetProcessInfo` 签名不变；`CommandLine`/`CreateTime` 的可观察行为（成功返回值、失败返回空串/0）与现状一致。

**验证**：
- `process_test.go` 扩展：对比 winapi 与 gopsutil 对同一普通进程 PID 的 Cmdline/CreateTime 一致
- 单独覆盖"系统进程（PID 4）→ CommandLine 返回空串"的降级路径
- `go test ./internal/core/` 通过
- **完成后 `grep -rn gopsutil --include="*.go" internal/core/` 应无结果**

**风险**：中。PEB 遍历涉及跨进程内存读取 + 32/64 位兼容，是本步最复杂的部分。但 gopsutil 现状就在做完全相同的事（行为不变量锁定为"权限不足返回空串"），有完整参照实现可逐行对照。

**为什么单独成步**：Cmdline 的复杂度比 Name/Exe 高一个量级，混在步骤 2 会模糊风险边界；单独成步便于独立验证和回滚。

---

### 步骤 3：端口枚举改原生 API（需用户协助验证）

**目标**：用 `GetExtendedTcpTable` + `GetExtendedUdpTable` 替换 `psnet.Connections`，砍掉 16.5% 分配。

**改动**：
- `winapi.go`：新增 `getExtendedTcpTable` / `getExtendedUdpTable`
  - 处理 `MIB_TCPROW_OWNER_PID` / `MIB_TCP6ROW_OWNER_PID` / `MIB_UDPROW_OWNER_PID` / `MIB_UDP6ROW_OWNER_PID` 四种结构
  - IPv4/IPv6 各调一次（AF_INET / AF_INET6）
  - 复用结果缓冲区（`ERROR_INSUFFICIENT_BUFFER` 两段式调用）
- `scanner.go`：`ListConnections` 改用 winapi，移除 `psnet` import
  - `FilterKind` 仍保留（语义不变），内部映射到 AF + table class

**字段映射的三个关键点（审查 Issue 2/3/4 修复）**：

1. **协议类型 Protocol**（审查 Issue 4）：原生 API 行结构**没有** Type 字段，协议类型由「来自哪张表」隐式确定——TCP 表（`getExtendedTcpTable`）出来的行填 `ProtocolTCP`，UDP 表（`getExtendedUdpTable`）出来的行填 `ProtocolUDP`。**删除 scanner.go:43-46 的 `c.Type == 2` 判定**。

2. **TCP 状态映射**（审查 Issue 3）：必须**逐值复刻** gopsutil 的 `tcpStatuses` 映射表（v4.26.7 `net_windows.go` 已核实，共 12 项），不能用省略号：
   ```
   MIB_TCP_STATE_CLOSED(1)      → "CLOSED"
   MIB_TCP_STATE_LISTEN(2)      → "LISTEN"
   MIB_TCP_STATE_SYN_SENT(3)    → "SYN_SENT"
   MIB_TCP_STATE_SYN_RCVD(4)    → "SYN_RECEIVED"
   MIB_TCP_STATE_ESTAB(5)       → "ESTABLISHED"
   MIB_TCP_STATE_FIN_WAIT1(6)   → "FIN_WAIT_1"
   MIB_TCP_STATE_FIN_WAIT2(7)   → "FIN_WAIT_2"
   MIB_TCP_STATE_CLOSE_WAIT(8)  → "CLOSE_WAIT"
   MIB_TCP_STATE_CLOSING(9)     → "CLOSING"
   MIB_TCP_STATE_LAST_ACK(10)   → "LAST_ACK"
   MIB_TCP_STATE_TIME_WAIT(11)  → "TIME_WAIT"
   MIB_TCP_STATE_DELETE_TCB(12) → "DELETE"
   ```
   - 注意 4→`SYN_RECEIVED`（非 SYN_RCVD）、6→`FIN_WAIT_1`、12→`DELETE`（非 DELETE_TCB）等与直觉不同的写法
   - **default 分支**（含 state=0 UNKNOWN 及任何未匹配值）→ 返回 `""`，再走 scanner.go:57-59 现有的 `=="" → "NONE"` 兜底

3. **UDP 状态**（审查 Issue 2）：原生 `MIB_UDPROW_OWNER_PID` / `MIB_UDP6ROW_OWNER_PID` **没有 state 字段**（UDP 无连接状态）。UDP 行的 `State` 直接置 `""`，沿用 scanner.go:57-59 现有的空串→`"NONE"` 兜底（或在原生层直接置 `"NONE"`）。**绝不能按 TCP 的方式给 UDP "映射 state"**——会导致空串或越界读。

**契约**：`ListConnections`/`FindPort` 签名不变，`Connection.State` 字符串格式逐值不变，`Connection.Protocol` 语义不变。

**验证**：
- 新增 `scanner_test.go`：
  - 解析伪造的 table 字节流，验证 4 种结构解析正确
  - **状态映射单测**：13 个状态码（1-12 + 0/未知）逐一断言输出字符串
  - **UDP State 单测**：UDP 行最终 State == "NONE"
- **⚠️ 需用户协助**：真实环境对比——改前后各跑一次，导出端口列表（PID + 本地端口 + 协议 + State），确认集合一致（**对比时务必包含 State 字段，不只比 PID 和端口**）
- `go test ./...` 通过

**风险**：中。涉及结构体内存布局（C 结构 → Go），字节对齐易错；状态映射须逐值复刻不能漏。但有 gopsutil 的结构定义可参照（`net_windows.go`）。

### 步骤 4：杀进程改原生 API

**目标**：`killer.go` 移除 gopsutil，用 `OpenProcess` + `TerminateProcess`。

**改动**：
- `killer.go`：
  - `PidExists` → 用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` 成否判断
  - `process.Kill` → `TerminateProcess(handle, 1)`
  - 保留第 2 级 `runas taskkill`（已是原生 ShellExecuteW，不动）

> **PidExists 语义差异说明**：gopsutil 的 `PidExists` 用 `OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject`，且对 `pid%4 != 0` 有"枚举全表二次确认"的特殊分支。本步改用 `OpenProcess` 成败判定，语义略弱。但 `killer.go` 即使误判"存在"，后续 `TerminateProcess` 失败会自然落到第 2 级 `runas taskkill`，最终观察到的 `KillResult.Message` 与现状基本一致，不影响可观察契约。

**契约**：`KillProcess`/`KillByPort` 签名与返回语义不变。

**验证**：
- `killer_test.go`（若可行，杀测试用子进程）：验证两级杀路径
- `go test ./internal/core/` 通过

**风险**：低。`TerminateProcess` 是 gopsutil.Kill 的底层实现，等价替换。

### 步骤 5：全局微调（零风险小优化）

**改动**：
- `main.go`：启动时 `runtime.SetMemoryLimit(64 << 20)` —— 给 Go runtime 设 64MB 软上限
- `groupmodel.go`：`aggregate()` 的 map 用 `clear()` 复用而非每次 `make`（Go 1.21+，go.mod 是 1.25 ✅）
- `scanner.go`：result slice 预分配容量（已 `make([]Connection, 0, len(rawConns))`，原生 API 改造后按 table 行数预分配）

**验证**：benchmark 对比。

**风险**：极低。`SetMemoryLimit` 是官方软限制，不会硬性 OOM。

**目标**：彻底从 `go.mod` 移除 `gopsutil/v4`（及随之可去的间接依赖）。

**前置条件**：步骤 1-2.5 全部完成，且 `grep -rn gopsutil --include="*.go" internal/` 无结果（步骤 2.5 解除了 core 包的最后一个 gopsutil 引用）。

**验证**：

**风险**：低。前置条件保证无残留引用。

> **关于间接依赖**：`go mod tidy` 会自动移除 gopsutil 带来的间接依赖（purego / go-ole 等）。注意 `jsonschema-go` 来自 `modelcontextprotocol/go-sdk`（MCP server 用），**不随 gopsutil 走，会保留**——这是预期行为，tidy 不会误删。
